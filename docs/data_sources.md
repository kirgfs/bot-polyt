### Почему задержка фида решает всё в лайве

В спорте маркетабельный ордер ждёт около 3 с, прежде чем сматчиться (`secondsDelay`, см. `docs/api_notes.md`, §12). После очка происходит следующее:
- быстрый тейкер отправляет ордер, но тот ждёт ~3 с;
- если наш путь «очко → событие в фиде → отмена подтверждена» укладывается примерно в `3 с − (задержка фида тейкера)`, мы успеваем снять котировку;
- если наш фид отстаёт на 5–15 с (типично для дешёвых фидов), каждое важное очко нас «выносит».

Отсюда правило из промта (§6.3): p95 задержки «событие → отмена подтверждена» — **гейт** для лайва. Порог — `secondsDelay` минус запас, по умолчанию ≤ 1.5 с. Если p95 выше, лайв-ММ по этому источнику выключается автоматически.

## 4. Методика замера задержки

### 4.1 Коэффициенты (OddsPapi)
1. Для каждого ответа REST и каждого кадра WS логируем `ts_recv_ns` — `time.time_ns()` при чтении из сокета на VPS. Часы синхронизированы через chrony, дрейф мониторит `core/clock.py`.
2. По каждой цене из ответа считаем [2nd, проверить наличие полей]:
   - `L_ingest = changedAt − bookmakerChangedAt` — сколько OddsPapi тратит на то, чтобы увидеть изменение у букмекера;
   - `L_e2e = ts_recv − bookmakerChangedAt` — возраст цены в момент, когда она у нас.

   При REST-поллинге `L_e2e` включает фазу опроса (до одного интервала), поэтому замер ведём сериями с частым опросом (§6, шаг 7) и отдельно указываем интервал.
3. **Lead-lag с Polymarket.** Сравниваем время движения линии Pinnacle со временем движения мида Polymarket (кросс-корреляция приращений). Если Polymarket систематически двигается раньше нашего фида, у нас нет информационного преимущества, и спред нужно расширять.

### 4.2 Счёт: «очко в реальности → событие в Sports WS» (решение 5)

Времени события в кадре Sports WS нет, поэтому нужен внешний эталон. Используем три, от основного к вспомогательному:
1. **Реакция книги Polymarket.** Первое заметное изменение книги после очка, гола или броска: мейкеры снимают уровни у мида (`price_change` с `size = 0` на лучших уровнях или скачок `best_bid`/`best_ask`).
   - Мейкеры отменяют сразу, без `secondsDelay`, поэтому реакция книги отстаёт от реальности только на задержку их фида `ℓ_fast`.
   - Мера: `Δ = ts_recv(кадр Sports WS со сменой счёта) − ts_recv(первая реакция книги)`. Это оценка снизу: истинная задержка = `Δ + ℓ_fast`.
   - Сопоставление очка и реакции: окно ±15 с, реакция — только на смену счёта (не на каждое движение книги); неоднозначные случаи отбрасываем и считаем их долю.
2. **Второй фид счёта.** Канал `scores` OddsPapi WS, если он будет в trial, или бесплатный тариф Live Tennis API. Сравниваем время одного и того же очка в двух фидах.
3. **Ручная выборка.** 30–50 очков по трансляции с отметкой времени. Точность ±1 с; нужна только для калибровки `ℓ_fast`.

Параллельно фиксируем **гранулярность** тенниса (приходят ли очки или только геймы) и долю пропущенных изменений счёта.

**Правило решения** (решение 5): если p95 `Δ + ℓ_fast` плюс время подтверждения отмены укладывается в `secondsDelay` минус запас, платный поочковый фид не нужен. Иначе выбираем платный фид в рамках бюджета (§2) или откладываем лайв.

## 5. OddsPapi: заметки по API для адаптера

> Все пункты — [2nd]: документация и блог OddsPapi через поисковую выдачу (сайт из облачного окружения недоступен). Проверяются первыми запросами на VPS (шаг 1 в §6). Адаптер ничего из этого не хардкодит без конфига: id видов спорта, рынков и слаги букмекеров лежат в `config/recorder.yaml`, при старте сверяются с `/sports`, `/markets` и `/bookmakers`.

- **База:** `https://api.oddspapi.io/v4`. **Ключ** — query-параметр `apiKey` (не заголовок).
- **Эндпоинты:**

  | Путь | Параметры | Что возвращает |
  |---|---|---|
  | `GET /sports` | — | Виды спорта: id и slug |
  | `GET /bookmakers` | — | 350+ букмекеров, среди них Pinnacle, Singbet, SBOBet, Betfair Exchange, Polymarket, Kalshi |
  | `GET /tournaments` | `sportId` | `tournamentId`, `tournamentName`, `categoryName`, `futureFixtures`, `upcomingFixtures` |
  | `GET /markets` | `sportId` | Каталог рынков вида спорта (id рынков и исходов) |
  | `GET /fixtures` | `sportId`, `from`, `to` (окно ≤ 10 дней, если нет `tournamentId`), `tournamentId`, `hasOdds` | Список матчей (поля ниже) |
  | `GET /odds` | `fixtureId`; опционально `bookmakers` (через запятую), `oddsFormat`, `verbosity` | Коэффициенты по матчу |
  | `GET /odds-by-tournaments` | `bookmaker` (ровно один), `tournamentIds` (через запятую) | Предстоящие матчи турниров с коэффициентами одного букмекера — дешёвый способ покрыть много матчей одним запросом |
  | `GET /historical-odds` | `fixtureId`, … | История; кулдаун 5 с |

- **Лимиты:**
  - free — 250 запросов/мес;
  - кулдаун между вызовами одного эндпоинта ~0.88–1 с на free, у `/odds` — 500 мс.

  Адаптер держит ≥ 1.1 с между вызовами и ведёт месячный счётчик запросов на диске.
- **Id:** футбол `sportId=10`, баскетбол `11`, теннис `12`.
  - Рынки: футбол 1X2 — рынок `101`, исходы `101`/`102`/`103` (хозяева / ничья / гости); теннис, победитель матча — рынок `171`, исходы `171`/`172` (игрок 1 / игрок 2).
  - Баскетбол moneyline — **id неизвестен**, берём из `/markets?sportId=11`.
- **Поля матча:**
  - основные: `fixtureId`, `participant1Id`/`participant1Name`, `participant2Id`/`participant2Name`, `sportId`, `tournamentId`, `tournamentName`, `categoryName`, `seasonId`, `statusId`, `startTime`, `updatedAt`, `hasOdds`;
  - **`externalProviders.betradarId`** (а также `sofascoreId`, `betgeniusId`, `flashscoreId`, `pinnacleId`) — ключ для точного сопоставления с `sportsradarMatchId` Polymarket.
- **Структура коэффициентов:** `bookmakerOdds.{slug}.markets.{marketId}.outcomes.{outcomeId}.players."0"`. Внутри: `price` (десятичный), `limit`, `active`, `changedAt`, `bookmakerChangedAt`.
  - `bookmakerChangedAt` — когда цену сдвинул сам букмекер;
  - `changedAt` — когда изменение увидел OddsPapi.
- **WebSocket:** `wss://api.oddspapi.io/v4/ws`.
  - Логин — сообщение с `type: "login"` и ключом, дальше подписка с фильтрами: каналы `odds`, `fixtures`, `scores`, `bookmakers`; `sportIds`; букмекеры.
  - Конверт кадра: `channel`, `type` (например, `UPDATE`), `payload`, `ts`, `entryId`.
  - Служебные кадры: `login_ok`, `snapshot_required`, `resume_complete`.
  - Кодировка JSON или MessagePack.
  - Доступ — на Pro или по запросу (B2B).

  Точный формат сообщений подписки не опубликован в выдаче. Поэтому рекордер умеет только писать сырые кадры WS, а сообщения логина и подписки задаются в конфиге после чтения документации на VPS.
- **Polymarket среди «букмекеров» OddsPapi.** Если в записи `bookmakerOdds.polymarket` есть идентификаторы рынков Polymarket, это бесплатная сверка нашего сопоставления. Проверить на шаге 6 §6.
